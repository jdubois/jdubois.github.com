Comment le faire vous-même

Six ingrédients pour l'ingénierie agentique.

De l'ingénierie agentique, pas du vibe coding

~2 000 $ de tokens sur tout le sprint — environ 9 $ par PR mergée. C'est la partie bon marché. La vraie question, c'est quand vous payez le code.

🎲 Vibe coding — peu cher au départ

  • Pas de specs, pas de harnais : vous commencez à livrer immédiatement
  • Vous payez en boucles de tentatives, puis à nouveau six mois plus tard en rétro-ingénierie d'un code que personne ne comprend
  • C'est la taxe de maintenance — invisible le premier jour

🏗️ Ingénierie agentique — payer d'abord

  • Specs, tests et CI vous coûtent de vraies journées avant que le premier agent ne tourne
  • Ils font itérer votre agent vers une solution solide, plutôt que de livrer à la hâte une réponse incorrecte
  • Le harnais demande un vrai investissement initial, mais s'en passer coûte plus cher ensuite
12 semaines et 552 PRs mergées de plus plus tard, la taxe de maintenance n'est toujours pas arrivée. C'est le harnais qui rembourse son coût initial.

Ingrédient

Écrire les spécifications

📜 Standards techniques · AGENTS.md

  • Définir les conventions une fois : stack, build, tests, style
  • Les instructions du dépôt définissent les règles, pas la procédure de chaque tâche
  • Des conventions par panneau pour que les 40 panneaux soient cohérents

🎯 Des spécifications métier complètes et claires

  • Quoi construire, où, et à quoi ressemble « terminé »
  • Des tests d'acceptation que l'implémentation doit passer, même en utilisant un skill
  • Petites, autonomes, sans dépendances cachées
La spec, c'est désormais le produit. Meilleur est le brief, moins vous avez à surveiller.

Ingrédient

Construire le harnais de tests

✅ Un build + des tests qu'ils peuvent lancer

  • Une seule commande lance la compilation, les tests unitaires et e2e : vert ou rouge
  • Les agents lancent les vérifications après avoir utilisé skills et outils, avant d'ouvrir une PR
  • Pas de tests = impossible de faire confiance au résultat

🛡️ La CI est la couche de confiance

  • ~116 suites de tests · ~81 Java + ~35 Playwright
  • CodeQL + e2e valident chaque PR vers main
  • C'est ce qui permet de merger ~20 PRs/jour en toute sécurité
Vous ne pouvez pas lire chaque ligne de 223 PRs. Un build vert auquel vous faites confiance, c'est ce qui rend ce volume relisible.

Ingrédient

Équiper vos agents

Tiré de mes sessions BootUI récentes : des skills réutilisables pour le workflow, de l'intelligence de code Java au besoin.

📚 Skills : des workflows réutilisables

  • Impeccable — créer de beaux designs Web, corriger les problèmes d'accessibilité
  • orchestrate — coordonner les audits des conseillers entre sessions
  • agent-merge — suivi des revues de PR, de la CI et des conflits
  • bootui-release — un skill sur mesure écrit spécifiquement pour guider une release de BootUI

🔎 LSP Java : de l'intelligence de code ponctuelle

  • Interroger le serveur de langage sur des symboles, pas seulement du texte
  • Utilisé pour explorer des modules Java avancés et inspecter le code pendant les revues
  • Le projet doit d'abord être indexé par le serveur de langage
Skills, serveurs MCP et outils connectent les agents à la documentation, aux données et aux systèmes externes.

Exemples enregistrés du 9 août au 8 septembre 2026, plus le skill de release sur mesure ; cela ne concerne pas le sprint d'origine.

Les exemples enregistrés reposent sur de véritables invocations d'outils dans des sessions BootUI du mois dernier, et pas seulement sur les skills installés. Impeccable a été invoqué le 26 août dans la session du thème Windows 95 et le 25 août dans la session de restructuration du site de documentation. Orchestrate a été invoqué le 7 septembre dans la session de coordination des audits des conseillers. Agent-merge a été invoqué à plusieurs reprises pour le suivi du cycle de vie des PRs ; certaines invocations sont des vérifications automatiques, et non des sélections manuelles explicites du skill. Le skill bootui-release, propre au projet, est un exemple supplémentaire, écrit pour guider une release de BootUI ; il n'est pas présenté comme une invocation observée dans cet échantillon. Le documentSymbol du LSP Java a renvoyé les plans des classes et méthodes du code CRaC, de la sécurité réactive et de la sécurité Quarkus lors de la revue du 15 août. Trois autres requêtes workspaceSymbol enregistrées n'ont renvoyé aucun résultat : ne pas prétendre que toutes les tentatives LSP ont aidé, ni que la navigation par références a été observée dans cet échantillon. D'autres skills apparaissent dans les enregistrements, dont bootui-vertical-pr, agentfinder et github-pr-media ; ce sont des exemples représentatifs, pas un inventaire complet ni une comparaison de productivité mesurée. Les skills apportent des procédures propres à une tâche et peuvent utiliser des outils ; le LSP apporte des informations structurées sur le code. Des outils spécialisés et des serveurs Model Context Protocol (MCP) peuvent exposer de la documentation, des données et des services externes aux agents. Ces intégrations étaient moins centrales pour BootUI, mais comptent davantage dans les workflows qui dépendent de systèmes externes. Ni les skills ni les outils ne remplacent les tests ou la revue. C'est l'ingrédient 4 : skills et outils aident les agents à agir, tandis que le harnais de tests vérifie s'ils ont réussi. Les deux font partie du harnais global de l'agent.

🧩 Préparer le travail en parallèle

  • ~40 panneaux quasi identiques = parfaits à répartir
  • Une tâche par agent : périmètre réduit, objectif clair
  • Une branche / un worktree chacun, sans collisions

🚀 Une flotte, pas un seul chat

  • GitHub Copilot App : de nombreux agents en direct sur une seule machine
  • Application mobile : des agents dans des conteneurs Docker, en déplacement
  • Votre débit, ce n'est pas votre clavier. Ce sont vos briefs.
Tout l'intérêt, c'est le parallélisme. Ne surveillez pas un agent. Lancez-en dix.

🖥️ Construisez avec GitHub Copilot App

L'application que nous avons utilisée tout au long du projet BootUI.

Votre espace de travail pour les agents de code IA

  • Planifiez les tâches et lancez des agents en parallèle, dans des worktrees isolés
  • Laissez les agents modifier le code et lancer les tests ; inspectez leurs diffs et relisez les PRs
  • Gardez planification, implémentation et maintenance au même endroit
Vous donnez la direction. Les agents font le travail. Vous relisez le résultat.
Inviter le public à scanner le QR code, qui renvoie vers la page officielle de présentation et de téléchargement de GitHub Copilot App. C'est l'espace de travail que nous avons utilisé tout au long de BootUI, de la planification et l'implémentation jusqu'à la revue et la maintenance continue. Cela ne signifie pas que chaque tâche a tourné en local ni que chaque PR a été créée par l'application. BootUI n'est pas qu'une étude de cas

Une console développeur locale pour Spring Boot 4 (MVC & WebFlux) et Quarkus.
