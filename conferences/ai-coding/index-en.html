What is BootUI?

"The missing developer UI for Spring Boot and Quarkus" — an embedded, local-only developer console that ships as a starter or an extension.

🧩 Multi-framework, multi-module

  • 15 Maven modules around one framework-neutral engine + a shared conformance suite
  • Spring Boot 4.1 (servlet and WebFlux) & Quarkus 3.33 LTS — same Vue UI, same REST contract
  • Java 17, Maven Central, full CI + CodeQL; GraalVM native, AOT and CRaC images

🖥️ ~67 feature panels

  • An embedded Vue 3 SPA — ~84 components — packaged in the starter
  • Each panel = backend endpoints + frontend view + tests, ×3 frameworks
  • Health, metrics, security & tuning advisors, vulnerabilities, SQL trace, Kafka/JMS, tracing…
  • Still the single biggest source of structural repetition

🤖 Built to be driven by agents

A local, opt-in MCP server lets Copilot or Claude Code run BootUI's advisors and read runtime diagnostics while fixing your code — plus a bundled agent skill and Coffilot, a Copilot canvas extension.
📦 Open source — github.com/jdubois/boot-ui  ·  270+ ⭐  ·  v1.15.0 (Aug 2026)  ·  docs at julien-dubois.com/boot-ui

🔧 Agent = model + harness

When an agent goes wrong, the reflex is to blame the model. Usually it's a missing tool, a vague rule or an absent guardrail. Most agent failures are configuration failures.

🧱 What a harness is made of

  • Rules — AGENTS.md, copilot-instructions.md, skills
  • Tools — the commands, MCP servers and APIs it can call
  • Sandboxes — where its code runs, what it can reach
  • Orchestration — sub-agents, model routing, hand-offs
  • Guardrails — deterministic checks it can never skip
  • Observability — logs, token and cost metering

🛠️ BootUI's harness

  • An explicit copilot-instructions.md every agent reads first
  • mvn verify + e2e specs the agent runs on itself
  • One worktree or container per agent — no collisions
  • Multi-module CI + CodeQL: nothing red reaches main
  • A conformance suite holding 3 runtimes to one REST contract
On Terminal Bench 2.0, a team moved a coding agent from outside the Top 30 to the Top 5 by changing only the harness — no model change at all. The harness is your surface area, not the model provider's.

📋 Context engineering — static vs. dynamic

  • Static — copilot-instructions.md, 63 lines, in every call. Paid every time, so it stays short
  • Dynamic — 6 *.instructions.md attach only when their applyTo glob matches. Quarkus rules never load for a Vue change
  • Progressive disclosure — a 160-line skill + a 40-line agent, pulled in only for the vertical-PR workflow

📐 Specs — the intent

  • docs/SPECIFICATION.md: 2,670 lines — the behaviour contract
  • PRODUCT.md + DESIGN.md carry product and visual intent
  • ~13,700 doc lines total, reviewed in PRs exactly like code

🛡️ Guardrails — the gate

  • build · CodeQL · cross-platform · JDK compat · OSV scan · Docker · Pages · release
  • A 566-line conformance catalog holds 3 runtimes to one REST contract
  • github-app.yml gives each agent its own worktree and Maven repo — no collisions
~220 lines of instructions steer 2,083 lines of CI and 641 test files. Context is a budget, not a document — the harness is cheap to write and expensive to skip.

🧠 Where the agents run — and what they cost

Coding agents live in three places. Most days I use all three, and they route to different models.

💻 In the editor

  • GitHub Copilot App on the laptop — many agents in parallel
  • Test the change live before I validate it
  • Conductor mode: I'm watching

⌨️ In the terminal

  • Copilot CLI for multi-file work across the 15 modules
  • It runs mvn verify itself and reacts to the output
  • Where the long, messy tasks go

☁️ In the background

  • Assign an issue from the mobile app, get a PR back
  • Dockerized containers — prototype on the go
  • Orchestrator mode: I'm not watching

🎛️ Model routing — don't pay frontier prices for a typo

  • GPT-5.5 Extra High Reasoning — most of the work, ~1.5M tokens (90% cached)
  • Claude Opus 4.8 & Gemini 3.1 Pro High — the trickiest parts, 3 models complementing each other
  • A smaller model / "Auto" mode for the deterministic tasks: boilerplate, test generation, review chores
💰 ~2,700M tokens (120M in + 15M out + 2,500M cached) ≈ $2,000 — about $9 per merged PR. Vibe coding is low CapEx / high OpEx: you pay later, in retry loops and maintenance. Agentic engineering is high CapEx / low OpEx — the harness is what makes the tokens land first time.

🔄 The agent loop

Kick off several agents at once. Each runs in a loop on its own branch or worktree: read the house rules, build, run the tests, open a PR, pick up the next task — many times over before you come back.
☕ Agent 1
A new panel: endpoints, DTOs, Java tests
loop ×6 · 6 PRs
🎨 Agent 2
The matching Vue view & e2e specs
loop ×5 · 5 PRs
🧩 Agent 3
Port it to Quarkus, same REST contract
loop ×7 · 7 PRs
📚 Agent 4
Docs, CHANGELOG, CI & release chores
loop ×4 · 4 PRs
Four agents looping → ~20 PRs a day. Your throughput isn't your keyboard anymore. It's how well you briefed them — and how fast you review.

🎢 The 80% problem

Agents produce ~80% of a feature almost instantly. The remaining 20% — edge cases, integration points, subtle correctness — is where your whole day goes. That's why the bottleneck moved to review.

✅ What the agent nails

  • The 67th panel, once the first six exist
  • Boilerplate, DTOs, mappers, wiring
  • Tests for the happy path
  • Porting a known contract to another runtime

⚠️ What still costs you

  • Wrong assumptions about business logic that look right
  • Ambiguity it never stopped to ask about
  • Missing edge cases and unrealistic error handling
  • Architecture decisions with a long maintenance tail

🧪 The study you should quote against me

METR found experienced developers were 19% slower with AI on tasks inside codebases they already knew deeply — the time went into verifying and correcting output. BootUI is the opposite case: massive repetition, broad-but-shallow integration, strong guardrails. That's the honest boundary of the 17–23× number.

📋 The 10 tips

1Write the house rules once — AGENTS.md / copilot-instructions.md. Keep it short: it's loaded on every call, so every token has to earn its place.
2Tests are your contract with the AI — they say what "correct" means far more precisely than any prompt. No agent without a build + test command it can run itself.
3One task per agent. Small scope, clear goal, its own branch or worktree.
4Run them in parallel. That's the whole point — don't babysit a single chat window.
5Keep PRs small. You can't review a 2,000-line diff twenty times a day.
6Let CI be the gatekeeper. Nothing reaches main red — that's what buys you the throughput.
7Pick the right model per task: cheap for boilerplate, strong reasoning for the hard 10%.
8Capture what works as skills — progressive disclosure: loaded when the task matches, not stuffed into the house rules. Repetition is where the leverage compounds.
9Re-brief instead of patching by hand. A bad PR is a briefing bug, not a coding task.
10Stay the architect. The design, the boundaries and the "no" are still yours.

📱 Assign an issue, close the laptop

  • Assign a GitHub issue to Copilot — from the mobile app if that's where you are
  • It provisions its own environment via copilot-setup-steps.yml, works on a branch, opens a PR
  • Actions run the same 11 checks; you get a green tick or a failure to read
  • Review, comment and merge from the phone — the loop never needs a terminal

🌱 Small work that never reaches me

  • Dependabot watches 6 ecosystems weekly — Maven, 4 npm trees, Actions
  • When a bump breaks the build, an agent picks the PR up and fixes it
  • Upgrades, flaky tests, docs drift: handled while I sleep
  • My attention goes to design and review, not chores
Parallelism isn't limited by my machine anymore. The runners are the machine.

🛡️ Review that scales with the output

More code per day means more risk per day. The only reviewer that keeps up is a machine.

🔍 CodeQL

  • Runs on every PR, not on a schedule
  • java-kotlin + javascript-typescript — both halves of the stack
  • 14 alerts found and fixed · 0 open
  • Alerts land in the PR, so the agent that caused it can fix it

📦 Supply chain

  • Dependabot: 6 ecosystems, weekly, auto-PR
  • A dedicated OSV live smoke workflow checks the advisory feed BootUI itself queries
  • Secret scanning + push protection: an agent cannot commit a credential
  • Pinned action SHAs, verified by a guardrail script

🧱 The rules of the road

  • Branch protection: nothing merges red — human or agent
  • CODEOWNERS and PR templates apply to agents too
  • Copilot code review comments on the PR before I open it
  • Every run is logged and replayable — the audit trail is free
I never chose these tools for the agents — they were already there. That's the advantage: the verification layer was built for humans at scale, and agents are just more of them.
